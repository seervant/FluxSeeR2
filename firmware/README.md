# FleXSeeR2 — прошивка

Настольный светодиодный ночник **FluXSeeR** (кодовое имя прошивки — **FleXSeeR**).

| | |
|---|---|
| Версия прошивки | **0.011.26.2** |
| Версия железа | **0.011.21** (21.11.2026) |
| Контроллер | ESP32-S3-DevKitC-1 (Liludin), ESP32-S3-WROOM-1 **N16R8** (16 МБ Quad flash + 8 МБ Octal PSRAM) |
| Среда | VS Code + PlatformIO, Arduino framework, ядро arduino-esp32 2.0.17 |

---

## 1. Сборка и прошивка

```bash
cd firmware
pio run                 # собрать
pio run -t upload       # прошить (разъём "UART" — мост CH343)
pio device monitor      # отладочный вывод (115200)
```

`Serial` выводится через **нативный USB** (разъём «USB»), прошивка идёт через
мост CH343 (разъём «UART»). Это разные порты, подключать оба одновременно не нужно.

Библиотеки тянутся автоматически: FastLED 3.9, Adafruit GFX, Adafruit SSD1306.

### Важно: каталог сборки вынесен из проекта

В `platformio.ini` есть секция `[platformio]`:

```ini
[platformio]
build_dir = ${sysenv.USERPROFILE}\.platformio\build_flexeer
```

Это **не перестраховка, а обязательное условие**. Линковщик ESP32
(`riscv32-esp-elf-ld`) собран под Windows с ANSI-функциями и не умеет работать
с путями, содержащими не-ASCII символы. Каталог проекта содержит кириллицу
(`Моя работка\Ночники`), и сборка падала на этапе линковки:

```
ld.exe: cannot open map file D:/-=SeeR=-/!??? ?????/.../firmware.map
```

Сами исходники при этом компилируются нормально — ломается только создание
файла карты линковки. Каталог сборки вынесен в ASCII-путь, и проблема исчезает
полностью. Если проект переедет в папку без кириллицы, секцию `[platformio]`
можно убрать — но лучше оставить: она защищает от повторного переезда.

Побочный эффект: если проект лежит в папке с кириллицей, команда
`pio run --project-dir "D:\Моя работка\..."` может не пройти — путь в аргументе
командной строки искажается. Надёжнее: `cd firmware`, затем `pio run` без
аргументов.

## 2. Питание

| Узел | Параметры |
|---|---|
| Аккумулятор | 4 x LiitoKala Lii-70S 26650 (7000 мАч), 4S1P, ~14.8 В номинал, 28 А·ч (103.6 Вт·ч) |
| BMS | 4S 40 А (Balance) |
| Преобразователь | TZT teng 300Вт 20А, понижающий 4S -> 5 В, КПД ~90 % |

### Бюджет тока

| Потребитель | Ток |
|---|---|
| 949 LED в худшем случае (белый на полную) | 56.9 А |
| Потолок преобразователя (непрерывно) | 15 А |
| ESP32 + периферия | ~1 А |
| **Бюджет на светодиоды** | **8 А** (40 Вт) |

8 А из пакета при КПД 96 % — это ~8.4 А от батареи, BMS 40 А перекрывает
с запасом вчетверо. Лимит 8 А выбран осознанно: это ночник, а не
прожектор; 40 Вт на светодиоды для настольной лампы более чем достаточно.

Ограничение реализовано дважды:

1. **Программно** (`ledsApplyPowerLimit`) — общий бюджет на **все 4 линии**
   сразу. FastLED в версии 3.10 считает лимит по одному контроллеру (одной
   ленте), а линий четыре — поэтому общий ток считается вручную по содержимому
   буферов, и при превышении картинка масштабируется **одним и тем же
   коэффициентом** для всех панелей и диска (иначе поверхности светились бы
   по-разному). Собственный лимитер FastLED отключён — он считал бы каждую
   линию отдельно.
2. **Аппаратно** — порог ограничения тока на преобразователе (см. ниже).

Из-за этого при 949 белых светодиодах на максимуме яркости картинка будет
масштабирована примерно до 14 % — это физическое ограничение питания, а не
ошибка. Ночью это как раз то, что нужно.

### Настройка преобразователя (у него есть и напряжение, и ток)

Обе ручки нужны, но работают они по-разному:

1. **Напряжение (CV) = 5.00-5.05 В** — выставить мультиметром, **без нагрузки**,
   потом проверить **под нагрузкой** (все 949 LED белым на максимуме).
2. **Ток (CC) = 10 А** — это порог защиты. Если нагрузка тянет больше,
   преобразователь не перегревается, а начинает **снижать выходное напряжение**
   (foldback). Лампа при этом не сгорит, но будет тусклой и «плавать».
   Рабочий ток 8 А берёт на себя программный лимит, CC = 10 А срабатывает
   только при КЗ или неисправности лент.
3. Если ток выставить слишком низко (например, 5 А), то при включении белого
   на максимуме напряжение сразу просядет — лампа будет мигать. Это не поломка,
   но выглядит как брак, поэтому порог ставим **выше** рабочего тока.

Схема получается правильная: WS2812B — это потребитель постоянного тока, но
нельзя включать его в режиме постоянного тока. Нужен именно **CV с потолком
по току** — то есть ровно то, что даёт этот преобразователь.

### Что ещё по питанию

- **Зарядка 4S-пакета.** ЗУ 16.8 В CC/CV (сетевой брусок, DC 5.5×2.1 мм) —
  балансировочного входа у него нет, выравнивание идёт пассивной
  балансировкой BMS. Подробно — `HARDWARE.md`, раздел 4.
- **Питание ESP32.** Если 5 В от преобразователя идут на плату DevKit, не
  подключайте USB одновременно — будет обратная подача в разъём. Варианты:
  питать DevKit от USB, а светодиоды — от преобразователя (земли объединить
  в одной точке у входа питания), либо диод Шоттки между 5 В преобразователя
  и выводом 5V платы.
- **Питание лент.** 8 А по проводам — это 2.5 мм² на шину и 1.5 мм² на
  ветку к панели. На каждую панель 16×16 и на каждое кольцо диска —
  отдельная пара проводов питания (инжекция), плюс электролит
  1000–4700 мкФ на шине.

## 4. Сервисный режим: проверка раскладки после сборки

Когда лампа собрана, направление прокладки ленты на диске и ориентацию панелей
нужно определить «на глаз». Прошивка для этого имеет **сервисный режим** —
перепрошивать под каждый вариант не нужно.

**Вход:** удерживать кнопку энкодера при включении питания (или удерживать её
2 секунды в обычном режиме). **Выход:** удерживать кнопку 2 секунды.

Экраны (сенсоры: левая TTP223 — назад, правая — вперёд; значение — энкодером):

| Экран | Что горит | Что проверяем |
|---|---|---|
| `SIDE COL` | весь столбец боковой матрицы (0..47) | какой столбец физически где — флаг `FLIP_X` |
| `SIDE ROW` | вся строка матрицы (0..15), ломаная линия | чётность «змейки» и вертикаль — флаг `FLIP_Y` |
| `DISK RING` | целиком кольцо диска (0 — центр, 7 — внешнее) | порядок колец — флаг `DISK_RING_REVERSED` |
| `DISK SEG` | один сегмент выбранного кольца | направление обхода — флаг `DISK_SEG_REVERSED` |

Все три панели 16x16 ставятся одинаково, поэтому `FLIP_X` / `FLIP_Y` — общие
на всю матрицу 48x16.

## 7. Тайминг анимаций: фиксированные 24 fps

> Раздел описывает **зафиксированную схему**. В сборке 0.011.22.2 планировщика
> кадров ещё нет — он реализуется следующим блоком кода (раздел 8).

Все эффекты считаются в **кадрах фиксированной частоты 24 fps**, а не по
реальному времени. Причина — не «24 вместо 28», а **постоянство шага**:

| | Как раньше | Как будет |
|---|---|---|
| Шаг анимации | `millis()` — время между кадрами гуляет (35 мс…70 мс) | ровно 1/24 с, всегда |
| Движение | слегка «дышит», на градиентах видно неравномерность | идеально ровное |

ТЗ требует «движение должно быть плавным» (эффект 2) и «непрерывным»
(эффект 3) — постоянный шаг это и даёт.

**Почему 24, а не 30.** Железный предел — длина самой длинной линии данных.
Топология: **4 линии** — три панели 16×16 по 256 LED и диск 181 LED. Передача
панели: 256 × 30 бит ÷ 800 кГц = **9.6 мс**, диск — 6.8 мс. `show()` ждёт
самую длинную линию, поэтому кадр при 24 fps (41.67 мс) — это 9.6 мс на
проводе и **32 мс запаса** на всю остальную работу: сенсоры, физика, чтение
карты, звук. На 30 fps (33.3 мс) запаса было бы 23.7 мс — впритык, когда
появится видео. 24 fps — с запасом.

Справочно: если бы все 949 LED висели на одной линии, предел был бы
35.6 мс на кадр → 28 fps, и запаса осталось бы всего 13 мс. Разбиение на
4 линии снимает это ограничение (потолок 104 fps), а ограничителем
становится работа кадра, а не провод.

**Как устроено.** Глобальный планировщик кадров в `main.cpp`: рендер
вызывается, только если с прошлого кадра прошло ≥ 41.67 мс. Эффекты получают
счётчик кадров и фиксированный шаг `dt = 1/24 с` и двигаются «за кадр».

**Скорости в параметрах остаются в «в секунду»** — числа на OLED не меняются,
меняется внутренний пересчёт:

| Параметр | В секунду | За кадр (1/24 с) |
|---|---|---|
| Z-радуга, скорость 32 | 256 оттенков/с (полный круг) | 10.67 оттенка/кадр |
| Z-радуга, скорость 8 | 64 оттенка/с | 2.67 оттенка/кадр |
| Жидкость | физика с шагом 1/24 с | — |
| Мячи в вакууме | шаг физики 1/24 с | — |

**Просадка кадров.** Долг не «догоняем» пачкой (это рывок), а сбрасываем,
если отстали больше чем на 2 кадра: при перегрузе анимация чуть замедляется,
но не дёргается.

**✅ Главный блокер снят в 0.011.22.2 — это был OLED, а не эффекты.**
Раньше `display()` библиотеки Adafruit отправлял весь буфер: 128 × 8 = 1024
байта; при `I2C_FREQ = 100000` это **92 мс блокировки** на обновление, а
обновление идёт каждые `DISPLAY_REFRESH_MS = 120` мс → **~77 % времени** и
92 мс — это 2.2 кадра при 24 fps, то есть анимация замирала на два кадра
каждые 120 мс.

Что сделано:
- **I2C 400 кГц** (`I2C_FREQ = 400000`) — в 4 раза быстрее; на шине нужны
  подтяжки ≤ 2.2 кОм (`../HARDWARE.md`, раздел 8.2);
- **постраничное обновление**: своя отправка через Wire — в шину уходят только
  изменившиеся страницы (0xB0|p, столбец 0, 128 байт), а если картинка не
  менялась — I2C не трогается совсем.

Итог: 92 мс → 3–6 мс на обновление, загрузка OLED 77 % → 1–8 %. Бюджет кадра
24 fps (41.67 мс) закрывается с запасом, **одной платы достаточно**
(`../HARDWARE.md`, раздел 11).

**Побочные плюсы.** Видео готовится под 24 fps — один кадр видео ровно на
один кадр анимации, без рассинхрона. Уровень звука для реакции эффекта на
музыку читается один раз за кадр (24 Гц достаточно). Физика мячей в ТЗ
описана как дискретная («на следующем кадре») — с фиксированным шагом
симуляция становится воспроизводимой.

### Эффект 2 «Динамическая Z-радуга» — 3 параметра

| Параметр | Диапазон | Что делает |
|---|---|---|
| `BRIGHT` | 1–16 | Общая яркость лампы |
| `SCALE` | 1–32 | Ширина видимой части спектра: 1 — почти ровный цвет, 32 — на всю лампу ровно один полный круг оттенков |
| `SPEED` | −32…+32 | Темп и направление движения; знак задаёт направление |

**Как считается.** Вся лампа разворачивается в один непрерывный путь по
поверхности: ряд матрицы `y = 0` (низ цилиндра) … `y = 15` (верх) → внешнее
кольцо диска → центральное кольцо. Всего 23 шага (`s`).

```
hue(s) = phase - s * delta
delta  = 8 * SCALE / 23      (оттенков на шаг пути)
phase  += SPEED * 8 * dt     (оттенков в секунду)
```

Знак скорости задаёт направление (по ТЗ):

| SPEED | Цилиндр | Верхний диск |
|---|---|---|
| `> 0` | снизу вверх | от внешних колец к центру |
| `< 0` | сверху вниз | от центра к внешним кольцам |

Оттенки соседних рядов и колец отличаются ровно на один шаг, поэтому
верхний ряд цилиндра и внешнее кольцо диска — это одна непрерывная радуга,
переходящая через край лампы (требование ТЗ «единая анимация»).

### Эффект 7 «Лавовая лампа» — 11 параметров

Физическая модель сгустков лавы, а не анимация. Файл — `src/EffectLava.cpp`.

| Параметр | Диапазон | Что делает |
|---|---|---|
| `BRIGHT` | 1–16 | Общая яркость (применяется централизованно) |
| `COVER` | 10–90 % | Доля площади матрицы, занятая лавой. **По умолчанию 50 %** — пузырьки никогда не заливают поверхность целиком |
| `COUNT` | 1–12 | Число сгустков |
| `SPREAD` | 1–16 | Разброс размеров: 1 — все одинаковые, 16 — от крошечных до крупных |
| `VISCOS` | 1–16 | Вязкость среды: сопротивление движению и затухание деформации |
| `ELAST` | 1–16 | Упругость: насколько быстро сгусток возвращает форму |
| `HEAT` | 1–16 | Скорость нагрева снизу и остывания сверху — задаёт темп конвекции |
| `MERGE` | 0–20 % | Частота слияний (редкое событие) |
| `SPLIT` | 0–20 % | Частота делений (очень редкое событие) |
| `SPEED` | 1–16 | Общая скорость движения |
| `COLOR` | 1–64 | Базовый оттенок лавы (кромка краснее, глубина желтее) |

**Модель сгустка.** Каждый сгусток собран из 5–10 капель (узлов) —
объединение кругов даёт неровный, вытянутый, асимметричный контур, а не
идеальный круг. Узлы смещаются от базовой формы (инерция движения) и
возвращаются пружиной (упругость), затухание задаётся вязкостью.

**Движение.** Температура стремится к равновесной для своей высоты (снизу
горячо, сверху холодно); горячий сгусток всплывает, остывший тонет — выходит
естественная конвекция. Соседи давят друг на друга при перекрытии (с
демпфированием относительной скорости — «лаву нельзя сжать») и притягиваются на
расстоянии (поверхностное натяжение). Масса пропорциональна площади, поэтому
тяжёлый сгусток смещается меньше.

**Слияние и деление.** Слияние возможно, когда сгустки глубоко перекрылись и
движутся медленно; площадь, масса, температура и скорость сохраняются,
контур собирается из узлов обоих. Деление возможно только у сильно растянутого
сгустка (часть узлов ушла от базовой формы) — площадь делится, половинки
расходятся в стороны.

**Площадь.** Закрашенная площадь измеряется после растеризации и сравнивается
с целевой: масштаб формы плавно подстраивается («лава несжимаема»). Суммарная
площадь держится на `COVER`, поэтому сгустки всегда занимают «свою» территорию
и не сливаются в сплошное пятно.

**Верхний диск** — вид сверху: тот же сгусток проецируется в полярные
координаты диска (высота → радиус, столбец → угол), поэтому масса выглядит
единой на боковой и верхней поверхностях.

> Шаг физики сейчас берётся по реальному времени (ограничен 8–50 мс), чтобы
> скорость не зависела от частоты вызовов. Когда появится планировщик
> фиксированных 24 fps (раздел 7), шаг станет постоянным.

## 9. Открытые вопросы

1. ~~Топология бакета~~ — **закрыто**: 4S1P, BMS 4S 40 А, преобразователь
   TZT teng 300Вт 20А.
2. **Направление прокладки ленты на диске** — определяется в сервисном режиме
   после сборки (экран `DISK RING` / `DISK SEG`).
3. **Ориентация панелей 16x16** — все три одинаковые, проверяется в сервисном
   режиме (экраны `SIDE COL` / `SIDE ROW`).
4. **Зарядка 4S-пакета** — нужен ЗУ 16.8 В или USB-C PD + контроллер заряда 4S.
5. **Уровни на энкодере**: если питание энкодера 5 В — нужны делители на A/B/S.
6. **microSD shield**: убедиться, что на шине SPI нет подтяжки к 5 В (MISO повредит ESP32).
7. **I2C-подтяжки**: при 4 модулях с родными 4.7 кОм суммарное сопротивление
   упадёт до ~1.2 кОм (ток > 3 мА) — подтяжки оставить на ESP32, с одного модуля снять.
8. **gm009605v4 — 0.96" I2C OLED 128x64**, а не SPI: интерфейс из ТЗ (раздел 4)
   придётся рисовать монохромным мелким шрифтом.
9. **Режим Octal PSRAM** собран с `memory_type=qio_opi` и `BOARD_HAS_PSRAM`;
   фактический режим проверить на железе (`psramFound()` / `esp32_get_free_psram()`).
10. **Ключ API убран из репозитория**: `KEY.txt` больше не отслеживается git, история переписана,
    в ветке `main` ключа нет; старый коммит с ключом ещё какое-то время доступен по прямой ссылке
    на GitHub. Удаление файла **не отменяет сам ключ** — старый ключ нужно отозвать у провайдера
    и выпустить новый, а хранить его вне репозитория (`.gitignore` строку `KEY.txt` содержит).
    Провайдер — **MiniMax API Platform** (глобальный регион: `platform.minimax.io`,
    API-хост `api.minimax.io`): это pay-as-you-go ключ с префиксом `sk-api-`; подписка
    M Plan использует отдельный ключ `sk-cp-` и на неё ротация не влияет.
    Ротация: Account → API Keys → Create new secret key → сохранить новый вне репозитория
    → удалить старый (старый ключ проверяется запросом к `api.minimax.io/v1/models`).
    **Ротация выполнена 22.11.2026**: старый ключ отозван в MiniMax (контрольный запрос
    даёт `HTTP 401`), новый pay-as-you-go ключ проверен (`HTTP 200`) и хранится вне
    репозитория; в git текста ключей нет.
